# 论文行文结构（D6 照这个填）

> **前提**：技术路线里那几块组件都不是新的（见 [文献库.md](文献库.md) §0.5 的新颖性审查）。
> 所以**行文的主线不是"我们提出了什么"，而是"我们做得比谁都干净，并且真的读出了数据里的东西"**。
>
> 本文档给的是**逐节结构 + 每节放什么证据 + 证据从哪来**。开赛 D6 直接照填。

---

## 0. 全文的一句话骨架

写摘要和引言时，让每一段都服务于这句话：

> 我们面对的是一个**企业真实场景**的预测问题。我们不追求提出新算法，
> 而是**把领域机制特征、状态空间潜状态、异构模型融合与成本敏感决策，严格地应用到这个具体业务问题上**，
> 用**对抗验证确认本地评估可信**、用**消融实验证明每一块都有边际贡献**、
> 用**多随机种子证明结果稳定**，并给出了〔**一个针对本赛题的具体发现**〕。

**最后那个方括号是全文的分数落点。** 开赛 D3–D5 的任务之一，就是把它填出来。

---

## 1. 逐节结构

### 摘要（**决定生死，最后写，但要写最久**）

五段式，每段都要有**具体方法 + 具体数值**：

| 段 | 写什么 | 反面教材（**别这么写**） |
|---|---|---|
| ① 总述 | 一句话点出赛题要解决什么 + 我们用什么框架 | "本文综合运用多种方法，深入分析了……" |
| ② 问题一 | 方法 + **具体数值结果** | "取得了较好的效果" |
| ③ 问题二 | 同上 | |
| ④ 问题三 | 同上 | |
| ⑤ 检验与创新 | 消融 / 稳定性 / 创新点三条 | |

- 关键词 3–5 个。
- **摘要里不许出现正文没有的创新点**。
- 数值一律写"较基线提升 X 个百分点"这种可核对的表述。

---

### §1 问题重述与分析

- 问题背景（**用业务语言，不是数学语言**）
- 三问逐条拆解 → 画一张**思路流程图**（评审很吃这个）
- **明确写出"我们把业务问题翻译成了什么数学问题"** —— 这是跨学科交叉的第一处体现

> 证据来源：`docs/问题理解.md`（G1 产出）

---

### §2 数据理解与可信性检验 ← **这一节是最大的差异化点**

**大多数队伍不写这一节。写了就赢在起跑线。**

| 小节 | 内容 | 证据文件 |
|---|---|---|
| 2.1 数据概况 | 样本量、特征量、缺失情况（表格 + 分布图） | `make data` 输出 |
| 2.2 数据清洗 | 每条处理规则的**理由**（不是"我删了它"，而是"为什么该删"） | |
| 2.3 **泄漏排查** | 四类泄漏逐条排查：预处理 / 目标编码 / 时序 / ID 顺序 | 排查记录 |
| 2.4 **对抗验证** | 训练集与测试集是否同分布？AUC 多少？哪些字段在漂移？ | `adversarial.json` + `adversarial_features.csv` |

> **2.3 和 2.4 是核心竞争力。** 写"我们发现问题并处理了"，比写"我们模型很准"有价值得多。
> 对抗验证的图直接放这里：漂移特征的重要度条形图。

---

### §3 特征体系

分三层写，**每层都要有"为什么这么设计"**：

| 层 | 内容 | 谁主责 |
|---|---|---|
| 3.1 通用特征 | 日期拆解 / 行内统计 / 缺失模式 / 频次编码 | CS |
| 3.2 **领域特征** | **机制驱动**——先讲"这个字段在现实中怎么产生的"，再讲特征怎么设计 | **A 生信** ← 跨学科交叉第二处 |
| 3.3 **潜状态特征** | 用状态空间模型拆出不可观测的水平/斜率/季节/周期 | **C 经济 + A** ← 跨学科交叉第三处 |
| 3.4 **消融实验** | 砍掉每组，主指标掉多少 | `ablation.csv` |

> **3.4 的消融表是"论证有说服力"的直接证据。**
> 别人说"我们加了 X 特征效果更好"，你说"砍掉 X 后主指标从 A 掉到 B，且降幅超过种子间标准差"。
> 后者才叫论证。表里要有：特征组 / 特征数 / 主指标 / 与完整模型的差。

---

### §4 模型建立与求解

| 小节 | 内容 | 证据 |
|---|---|---|
| 4.1 模型选择 | **为什么要对比这几个**，为什么没选深度学习（引 Grinsztajn 2022 / TabArena 2025） | |
| 4.2 参数设置 | **说明参数有出处**（引 Holzmüller 2024 的预调默认值），不是拍脑袋 | `config_used.yaml` |
| 4.3 交叉验证方案 | 切分策略 + **为什么这么切**（含分组/时序的处理） | `metrics.json` |
| 4.4 融合与门控 | 四方案对比表（最好单模型 / 简单平均 / 线性堆叠 / 软门控）+ **术语说准** | `fusion.json` |

> ⚠️ **4.4 的术语必须精确**（见 [技术路线.md](技术路线.md) §2.6）：
> 只看预测的叫 stacking/DES；看特征的才叫门控/MoE。**写错了会被懂行的评审抓住。**
> 若软门控没赢过线性堆叠，**如实写**，别硬吹。

---

### §5 决策层：成本敏感的阈值

- 默认 0.5 阈值只对"误判代价对称"成立
- 给出期望损失公式：`E[损失](t) = C_FP · FP(t) + C_FN · FN(t)`
- 画出**阈值 vs 期望损失**曲线，标出最优点
- 用业务语言解释**这个阈值意味着什么**

> **这是经济哥的主场，也是"把一个模型升级成解决一个问题"的地方。**

---

### §6 模型检验与灵敏度分析

| 检验 | 怎么做 | 证据 |
|---|---|---|
| 稳定性 | 3 个种子报"均值 ± 标准差" | `metrics.json` 的 `per_seed` |
| 阈值敏感性 | 阈值 ±10% 时结果怎么变 | §5 的曲线 |
| 分群分析 | 不同难度档里最优专家会换人吗 | `gating_analysis.csv` |
| 亚群识别 | 门控权重聚类出的样本分群 | `gating_subgroups.csv` |

> 分群分析若显示"**不同难度档里最优专家会换人**"，那就是门控有存在必要性的实证，
> 也是全文"样本异质性"那一节的落点。

---

### §7 模型评价与推广

- 优点（**要具体**，不要"精度高、泛化好"这种空话）
- **缺点与边界条件**（诚实写 —— 评审吃这个，比吹优点加分）
- 改进方向
- 推广价值（换个业务场景还能用吗）

---

### §8 结论

- 三问的结论各一句，**带数字**
- **那个"具体发现"在这里收口**

## 2. 三个必须写进去的"诚实段落"

这三段是**加分项，不是减分项**。主动写，评审会觉得你们可信。

1. **边界条件**：什么情况下我们的方法会失效？
   （例："当序列短于一个完整季节周期时，潜状态特征的优势消失"）
2. **已知缺陷**：哪个判据在我们这个规模上失效了、为什么。
   （对应 [门控系统.md](门控系统.md) 的"如实登记缺陷"原则）
3. **未做到的事**：如果有组件没赢过基线，明确说。

> 用 [技术路线.md](技术路线.md) §6 的**伪创新检验句**照一遍每条创新点：
> **"当机制从 A 变到 B 时，指标从 X 变到 Y，因为〔解释〕；在 Z 条件下优势消失。"**
> 填不满的，不要写进创新点。

## 3. 分工 —— **但先读 AI 合规约束**

> 🔴 **MathorCup 2026 官方《人工智能工具使用规定》要求：
> "核心建模、算法设计、求解与分析由参赛队员独立完成"**；
> 且 AI 辅助的代码要在注释注明、必须提交《AI工具使用详情说明》PDF、
> 不合规**取消评奖资格**。（详见 [赛制与学术风险清单.md](赛制与学术风险清单.md) §1）

**这条规定如果适用于大数据竞赛**（待确认，但按最坏情况准备），
那么"AI 写草稿、你们改改"这种做法是**有风险的**。所以分工按下面的**合规版**来：

### 合规版分工

| 环节 | AI（我）的角色 | **必须由队员做** |
|---|---|---|
| D1 读题 | 整理赛题原文要点、列出**候选**建模方向 | 🔴 **选定方向并说明理由** |
| D1 数据 | 跑工具、出体检结果 | 🔴 **判断字段的业务含义** |
| D2–D3 特征 | 写特征代码、跑消融 | 🔴 **领域特征的设计思路** |
| D3–D5 建模 | 跑实验、汇总证据、列出**候选**融合方案 | 🔴 **决定用哪个方案、为什么** |
| D5 解读 | 出门控分群表、重要性表 | 🔴 **结果解读与业务解释** |
| D6 论文 | 提供**结构与数据表**、检查格式 | 🔴 **正文由你们写**（尤其分析、论证、结论） |
| D7 交付 | 跑复现校验、按清单核对 | 🔴 **最终确认提交** |

### 具体怎么落地

1. **决策留痕**：每次选方案，写一句"我们选 X，因为 Y（业务/数据理由）"，
   记在 `docs/决策记录.md` 里。这既是合规证据，也是论文素材。
2. **代码要读懂**：CS 哥对每一段关键代码能讲清楚在干什么，而不是"AI 写的能跑就行"。
3. **论文正文由你们写**：我最多给"这一节该放什么表、什么图、引用哪几篇"，
   **分析和结论的文字不要我代笔**。
4. **如实准备《AI工具使用详情说明》**：工具名称/版本、用途与阶段、关键交互记录、
   采纳了什么、人工修改了什么。**从今天开始记，别到 D7 补**——补不出来。

> **我写不出你们的领域判断和业务解释，那本来就是你们的分数。**
> 体力活（代码、实验、格式检查）交给我；**判断和文字，你们自己来。**
> 这样既合规，论文也更像"你们写的"——本来也该是。
